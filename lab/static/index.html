      2 · Verified auto-tuner (the LLM proposes, the simulator decides)

      Claude reads measurements of the workload and proposes 3 settings for K, the HIGH deadline and aging. A classical grid search competes with it. Every candidate is then re-measured on random workloads nobody tuned on, and it is only accepted if it beats the default settings there.

      The problem

      SCAN (the elevator) minimises arm movement but treats every request the same. So a page fault (the CPU is blocked waiting for it) can sit behind 40 requests from a backup job that happen to lie in the arm's path.

      PA-SCAN-BT = LOOK + three rules

      1. Priority guard. Before each normal step: "would serving the next request in sweep order make any HIGH request miss its deadline?" If so, go to that HIGH request now.
      2. Burst-throttling. Per sweep, a LOW process gets at most K requests and a MEDIUM process 2K. The rest wait for a later sweep, so one process can no longer hold the arm hostage.
      3. Aging. After waiting longer than the aging limit, a request can no longer be throttled. Nothing starves.

      Switch all three rules off and you get exactly LOOK. That is how the ablation study isolates each rule.

      The AI co-pilot: an LLM working for the OS

      The lab also runs the other direction: an LLM helps a human operate the scheduler. It builds workloads from English, explains individual decisions, and suggests tuning values. It is never trusted blindly. Its specs are clamped to safe ranges, and its tuning ideas must beat the defaults on unseen workloads before they are accepted. With no internet it falls back to offline engines (keyword parser, rule templates, grid search).
